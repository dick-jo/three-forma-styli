# Technical and product audit — 2026-07-21

> Historical snapshot: this document records the repository state at the start of
> the cleanup. See [audit-2026-07-22.md](./audit-2026-07-22.md) for the verified
> post-implementation state. In particular, the typography section and test counts
> below are no longer current.

## Executive assessment

Three Forma Styli is useful, but it is not yet a general-purpose replacement for
Style Dictionary, Terrazzo, or Tokens Studio. Its defensible value is narrower and
more interesting: it generates a constrained design system from a small,
TypeScript-native set of inputs, especially luminance-related OKLCH colors,
alpha schedules, and coordinated modes. The established tools are strongest at
transporting and transforming tokens that already exist; TFS is strongest when
it acts as an opinionated *system generator*.

That is not pointless reinvention. It becomes reinvention if TFS grows its own
non-standard interchange format, generic plugin framework, or full design-tool UI.
The recommended product boundary is:

- author a small, typed, opinionated source model;
- generate a stable intermediate representation;
- emit standards-based DTCG plus focused first-party CSS/Figma adapters;
- interoperate with broader ecosystems rather than copying them.

The repository was a credible prototype with a sound three-layer direction, but
it had release, validation, documentation, and abandoned-code failure modes that
made it unsafe to market as a gold-standard toolkit. The highest-risk discovered
issues have been repaired in the current cleanup branch; the remaining work below
should be handled before a 1.0 claim.

## Production compatibility boundary

The only identified production consumer is `~/project-local/splinter` (Scatter):

- `apps/main/package.json` depends on `@three-forma-styli/core@^0.1.3`.
- Runtime theme code imports `generate`, `toCss`, `oklchToCss`, `validateLuminance`,
  `Oklch`, and `PartialDesignSystem`.
- `apps/main/src/css/system.tokens.css` is checked in and identifies CLI v0.1.4.
- The app does not depend on `@three-forma-styli/cli` or
  `@three-forma-styli/themes` at runtime.
- The Splinter worktree was already heavily modified during this audit, so no
  production files were edited.

The current core changes are additive for those imports. One intentional visual
behavior change is retained: native `oklch()` output no longer round-trips through
sRGB. That round-trip clipped wide-gamut colors and explains the previously dull
output. Hex and RGB output remain gamut-mapped to sRGB. Display-P3 component bytes
are preserved for profile-aware JSON/Figma output and rejected by the
`generateCss()` convenience path.

## Findings repaired during this audit

### Release and package integrity

- The feature branch and `master` pointed to the same commit; all Figma work was
  uncommitted. The work was reviewed as source, not assumed to be branch history.
- Registry dependency ranges made the CLI compile against the old published core
  instead of the local workspace, breaking the monorepo build. Internal packages
  now use `workspace:^`, which pnpm rewrites on pack/publish.
- Builds did not clean `dist`. The themes tarball leaked removed `scatter-2` and
  `scatter-3` builds, and the CLI leaked a removed template. Builds now clean first.
- The packages had no included license files, repository metadata, public publish
  config, root verification command, or documented release procedure. These are
  now present.
- The old esbuild dependency had a published security advisory. It was upgraded;
  the production dependency audit now reports no known vulnerabilities.
- `publint` now passes for core. All packages are intentionally ESM-only; CommonJS
  callers must use dynamic import.

### Figma and DTCG

- The previous “DTCG” output placed hex strings in color `$value`, which is invalid
  under DTCG 2025.10. It now emits typed color objects and the official schema URL.
- Generator metadata previously occupied an invalid `_meta` pseudo-group in DTCG.
  It now uses a vendor-namespaced `$extensions` member.
- Color modes now retain typed color values under a namespaced extension, while
  the separate Figma Variables model supplies every mode value required by the API.
- The sync instructions said only `file_variables:write`; the implementation also
  performs GET and therefore requires `file_variables:read`.
- Dry-run incorrectly required a token. It no longer does.
- Renaming Figma's initial “Mode 1” could also create a duplicate mode. The payload
  algorithm and regression tests now cover this case.
- The color-profile contract is explicit: `srgb` and `display-p3` are distinct,
  and P3 component values must target a P3-profile Figma file.
- The feature now has transformer tests, sync-payload tests, build smoke tests, and
  a successful tokenless dry run. A live Enterprise Figma write has not been run.

### Workspace quality

- Core had 112 pre-existing tests but none for the abandoned Figma code. The suite
  now has 121 core tests plus 4 CLI sync tests.
- The preview app imported a removed API and had 12 hidden type errors while Vite
  still exited successfully. `svelte-check` is now part of root verification and
  the preview reports zero type errors.
- Two contradictory public `GeneratorConfig` interfaces existed. The stale one was
  removed, and `GeneratorOptions` now models deeply optional user input while
  `GeneratorConfig` remains the resolved internal shape.
- The generated `tfs init` config used the wrong type and would reject documented
  selector options. It now uses `GenerateCssConfig`.

## Open engineering risks

### Priority 1 — correctness and safe evolution

1. **Mode identity can collide across categories.** `IR.overrideTokens` is keyed
   only by mode name. A color mode and size mode with the same name can be merged
   and then assigned a single selector category. The IR should key overrides by
   category and mode, or validation must reject cross-category collisions before
   the next release.
2. **Validation is incomplete.** Duplicate mode names/defaults, unsafe token names,
   non-finite OKLCH values, missing named spacing references, and out-of-range gap
   references are not consistently rejected. Some paths silently fall back.
3. **The sync command is additive, not fully declarative.** It creates and updates,
   but does not remove stale Figma variables or modes. Destructive reconciliation
   needs an explicit opt-in plan and tests; current docs state the limitation.
4. **No live Figma contract test exists.** The local payload matches the current
   REST schema, but an eligible Enterprise file is still required to validate a
   real create/update cycle and P3 appearance.
5. **No compatibility fixture protects Scatter.** Add a checked-in consumer fixture
   that compiles the exact imports and snapshots representative generated CSS.
   Release candidates should also be installed into Splinter by exact version.
6. **Versioning is manual.** Introduce Changesets (or an equivalently explicit
   release mechanism), changelogs, prerelease tags, and provenance after the first
   cleanup release. Do not automate `latest` publication before the canary path is
   proven.

### Priority 2 — API coherence and maintainability

1. `modeCategories` exists in generator configuration but is not used to construct
   the IR or transformer behavior.
2. Time “modes” are actually prefixed token families emitted together at root, not
   selectable modes. The naming and architecture docs should be corrected or the
   behavior redesigned.
3. `generateCss()` and the CLI require a full `DesignSystem`, while lower-level
   `generate()` supports `PartialDesignSystem`. Convenience APIs should be coherent.
4. CLI theme loading is duplicated between build and Figma sync, uses broad `any`,
   calls `process.exit()` inside command logic, and uses timestamp-only temp names.
   Extract a typed loader and return/throw errors so commands are unit-testable.
5. The Figma serializer is color-only. That is honest for Variables, but the DTCG
   serializer should eventually support all existing token families using official
   dimension and duration types.
6. The preview production build still reports old-browser CSS-nesting target
   warnings. Its supported browser target and nested selectors need alignment.
7. Package docs and architecture notes were substantially stale. The most visible
   inaccuracies are fixed, but all examples should become executable documentation
   tests rather than prose that can drift.
8. ESM-only support is acceptable, but it must remain explicit. If CommonJS becomes
   a product requirement, publish a real dual build rather than relying on `main`.

## Typography assessment

Scatter's current typography layer is not “terrible”; it already contains the seed
of the right abstraction: font faces, family roles, size primitives, and composite
role/size recipes. The problem is that the generator stops at numeric `--fs-*`
primitives, so the semantic layer is hand-built and inconsistent.

Measured in the current Splinter worktree:

- 32 CSS files reference raw `--fs-*` values;
- there are 107 raw `--fs-*` references;
- there are 355 references to the hand-authored `--font-*` recipes;
- typography CSS applies broad element rules (`span`, `p`, `a`, headings, and `*`),
  producing specificity workarounds in components;
- the `font` shorthand recipes reset unrelated font subproperties and make small
  local overrides harder to reason about;
- recipe names mix visual size (`min`, `s`, `l`, `max`) with semantic role, so a
  component still decides typography by pixel fit rather than content purpose.

The universal system should have three explicit layers:

1. **Font assets and metrics** — typed `@font-face` sources, weight/style/stretch
   ranges, display policy, and optional fallback metric overrides. Scatter's files
   include variable Work Sans and JetBrains Mono fonts plus discrete PP Nikkei Maru
   300/400/800 cuts; the config must make invalid requested weights impossible.
2. **Primitives** — named font families, available weights, line-height and tracking
   scales, plus static or fluid size steps. Fluid viewport interpolation should be
   optional (Utopia-style), not conflated with accessibility/user size modes.
3. **Semantic recipes** — names such as `body-default`, `body-compact`,
   `label-control`, `label-meta`, `heading-section`, and `heading-display`, each
   resolving family, weight, size, leading, tracking, transform, and optional
   variation settings. Components consume recipes; raw primitives are reserved for
   defining or exceptionally extending recipes.

CSS should emit longhand custom properties and optional generated recipe classes,
not only a `font` shorthand. Font metrics should inform fallback `size-adjust`,
`ascent-override`, `descent-override`, and `line-gap-override`; cap-height-aware
alignment can integrate ideas from Capsize without reimplementing its font parser.

The first implementation should be additive: preserve existing `--fs-*` output,
add asset/family/recipe output, migrate a small representative set in Scatter, and
only remove legacy recipes after visual regression coverage.

## Recommended sequence

1. Merge this cleanup/Figma work, but do not publish `latest` yet.
2. Fix mode identity and input validation, then add a Scatter compatibility fixture.
3. Make the new CI workflow a required GitHub check and add package-lint enforcement.
4. Implement additive typography assets + semantic recipes with golden CSS tests.
5. Trial the typography API on several unlike Scatter components (body copy,
   controls, dense metadata, section headings, and display text).
6. Publish a `next` core version, install it exactly in Splinter, regenerate and
   review CSS, run visual QA, then promote it.
7. Expand DTCG to all token families and consider importing standard DTCG only after
   the core model and typography vocabulary stabilize.

## Product positioning

TFS should not compete on “we can turn arbitrary tokens into 30 platforms.” Style
Dictionary and Terrazzo already occupy that space, and Tokens Studio owns a mature
Figma-centric authoring workflow. TFS can credibly compete on “a small set of
perceptual and semantic decisions expands into a disciplined, runtime-themeable
system, with first-class CSS and standards-based escape hatches.”

That is a real and useful product, particularly if the preview becomes a constraint
editor and diagnostic tool rather than a generic token spreadsheet.
